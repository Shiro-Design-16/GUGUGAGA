# ググガガ語（中国語表記：咕咕嘎嘎語）の VS Code サポート

このディレクトリは言語プロジェクトのエディタ側の付属物です：`.咕咕` / `.ググ` / `.gu` / `.gugugaga` のファイルを VS Code に入れるだけで、ハイライト、補完、ホバー、構文チェックが効きます。三つの方言（中国語 咕嘎、日本語 グガ、英語 GU/GA）は同じファイルの同じ語の中に混ぜて書け、拡張機能はそのすべてを認識します。これは**インタプリタではありません**。プログラムを走らせるのは今も `咕咕嘎嘎 程序.咕咕` です。

| パス | 何か |
| --- | --- |
| `gugugaga/` | 拡張機能の本体：マニフェスト + 7 個の JS モジュール + 文法 / スニペット / 言語設定 + 11 個のテストファイル |
| `gugugaga-language.vsix` | ビルド済みのインストールパッケージ（19 エントリ、約 35 KB） |
| `build-vsix.sh` | パッケージングスクリプト：`gugugaga/` の中で実行時に必要なファイルを zip に詰める |
| `CONTRACT.md` | 着手前に決めたインタフェース契約と検証チェックリスト（歴史的文書で、末尾に改訂履歴あり） |

## インストール

```bash
code --install-extension vscode/gugugaga-language.vsix      # 在仓库根执行
```

VS Code の「拡張機能」ビュー → 右上の `...` → **VSIX からのインストール** で、このファイルを選ぶ方法でも構いません。インストール後に任意の `.咕咕` / `.ググ` / `.gu` / `.gugugaga` ファイルを開くと、ステータスバーの言語モードに「咕咕嘎嘎语」と表示されます。

## 六つの機能

| 機能 | 具体的な挙動 | 実装場所 |
| --- | --- | --- |
| 言語の基本 | 四つの拡張子（`.咕咕`/`.ググ`/`.gu`/`.gugugaga`、大文字小文字を区別しない）、`：` または `:` で終わる行の自動インデント、`嘎嘎`/`嘎嘎嘎嘎`/`嘎嘎嘎嘎嘎嘎` によるインデント後退（日本語 ガガ、英語 GAGA でも同じ）、インデントによる折りたたみ、単語規則が 咕/グ/ぐ/GU と 嘎/ガ/が/GA を同時に認識、コメント構文なし；マニフェストには `.ググ` の分解表記（macOS ではファイル名が ク + ゛ の二つの符号位置になることがあります）も登録し、拡張子を判定できなかった文書は実行時に NFC 正規化してからもう一度判定します | `gugugaga/language-configuration.json` |
| ハイライト | 30 個の予約トークン + 二種類のリテラル（ビット列はまとめて着色）+ クラス名 / メソッド名 / 変数名 + `！？`/`：` の約物、35 条のフラットな規則；各規則は 咕/グ/ぐ/GU、嘎/ガ/が/GA、全角 / 半角の `！？：`/`!?:` を同時に扱い、`GU`/`GA` は二文字で一つのトークン | `gugugaga/syntaxes/gugugaga.tmLanguage.json` |
| 補完 | コンテキストに応じて予約語、骨格スニペット、その文書で定義済みの名前を提示；`！？` の直後はメソッド名だけ | `gugugaga/src/completion.js` |

実行ボタンは**出力をキャプチャしません**：プログラムが吐くのはビットストリームだけですし、stdin を食わせ、自分で `| ggt decode --bytes` に繋ぎ、終了コードも見られるのはターミナルのほうです。コマンドラインは**暗黙実行**（ファイルパスだけを渡し、動作語 `嘎嘎` は付けません）を使い、組み立て時に POSIX/win32 の規則で引数をクォートするので、パスに空白があっても崩れません。キーボードにはショートカットを割り当てていません：コマンドパレットに ASCII のキーバインドを含む項目があると、純粋性が壊れるからです。

ほかに 8 条のスニペット（クラス、コンストラクタ、メソッド、エントリ、フィールド、条件、ループ、インスタンス生成式）が付いていて、その本文は 咕/嘎/！/？/：/空白/改行 だけで書かれています。

## 三つの方言

| ビット | 中国語 | 日本語 | 英語 |
| --- | --- | --- | --- |
| 0 | 咕 | グ / ぐ | GU / gu |
| 1 | 嘎 | ガ / が | GA / ga |
| 約物 | ！ ？ ： | ！ ？ ： | ! ? : |

同じファイルの同じ語の中でも混ぜて書けます（`グ咕GU！` は一つの宣言ヘッダです）。内部では一律 咕/嘎 に正規化されるので、補完候補、ホバーの意味説明、診断の本文は今も規範の中国語表記です。拡張子 `.咕咕` `.ググ` `.gu` `.gugugaga` は大文字小文字を区別しません；コマンド名は `咕咕嘎嘎` のほか、日本語の別名 `ググガガ`、ラテン文字の旧名 `gggg`、`gg` も認識します。

## 外殻の純粋性：どの字が咕嘎で、どれが ASCII でなければならないか

**咕嘎 で書かれているもの**（ユーザーの目に触れるものすべて）：`displayName`、コマンドのタイトル、出力パネルのタイトルと内容、Problems パネルのソース列（診断コレクション名 `咕咕嘎嘎`）、5 個の設定のグループ見出し、スニペットの `description`、補完候補の `detail`/`documentation`、ホバーの文案、`cliPath` の既定値（`咕咕嘎嘎`）。パネルに書く前には実行時のゲート `isPureLine()` もあり、咕/嘎/！/？/：/空白 以外を含む行はパネルに書かず開発者コンソールにだけ出します；`tests/purity.test.js` は変異テストで、このゲートが実際に拒むことを示します。

**ASCII のままでなければならないもの**：拡張機能の `name`/`publisher`、`engines.vscode`、`main`、`activationEvents`、`languages[0].id`、`grammars[0].scopeName`、コマンド id、設定 id と `type`/`scope`。これらは文案ではなく **VS Code schema の照合キー** です——拡張機能の識別子、アクティベーションの契機、TextMate `source.gugugaga` のインジェクション、コマンドパレット API は、どれもこの文字列で照合され、一文字でも変えると拡張機能が読み込まれません。同じ理由で、`nodePath` の既定値は `node` しかあり得ません。

Problems パネルに出るものも**中国語ではありません**：診断項目の本文は、その診断の**フレーム全体の生のビット列**（純粋な 咕/嘎）で、コード名列は空にしてあります（そうしないと `E1001` のような ASCII が描画されてしまう）。人間の読める文が欲しければ、そのビット列を姉妹プロジェクトのトランスレータに渡します：

```sh
ggt decode --diag <<< "嘎咕嘎咕咕咕…"     # → 2:7 E1001 非法字符“噶”（U+5676）
```

この取捨は意図的です：エディタに残る可視面は言語そのものと同じくらい純粋で、人間向けの文はトランスレータからしか出てきません。代償は、ホバーで見えるのがビット列だということです——拡張機能は「ついでに翻訳」を意図的にやりません。そんなことをしたら、トランスレータの存在意義が失われます。中国語の本文とコード名は開発者コンソール（`console.error`）にも出るので、原因を追うときは DevTools を開けば見えます。

## 診断はどうやってインタプリタを見つけるか

拡張機能は自分では構文解析器を実装していません——診断は完全に本物のインタプリタから来るので、コマンドに到達できる必要があります（三段階のフォールバック）：

| 優先度 | 条件 | 実際の実行 |
| --- | --- | --- |
| 1 | 設定 `gugugaga.cliPath` の値が既知のコマンド名（`咕咕嘎嘎`/`ググガガ`/`gggg`/`gg`）ではなく、かつそのパスが存在する | そのまま実行；`.ts` で終わるなら `<nodePath> <该路径> 嘎嘎 <文件>` |
| 2 | ワークスペースのルートに `bin/gg.ts` がある | `<nodePath> <工作区>/bin/gg.ts 嘎嘎 <文件>` |
| 3 | どれも成り立たない | PATH 上で `咕咕嘎嘎` → `ググガガ` → `gggg` → `gg` の順に、最初に見つかったものを使う |

動作語は規範の書き方 `嘎嘎`（= 検査のみで実行しません）；`check` はインタプリタが予約しているラテン文字の別名で、拡張機能は使いません。

起動に失敗してもタイムアウトしてもダイアログは出さず、出力パネルにも書きません（パネルは 咕/嘎 しか許しません）：詳しい原因（exec、args、ワークスペース、スタック）は `console.error` に出るので、VS Code の「ヘルプ → 開発者ツールの切り替え」で見ます。

## 再パッケージング

```bash
./vscode/build-vsix.sh                        # 输出 vscode/gugugaga-language.vsix
unzip -l vscode/gugugaga-language.vsix        # 看包内清单
unzip -p vscode/gugugaga-language.vsix extension.vsixmanifest   # 看 VSIX 清单
```

スクリプトはまず必須ファイルを事前チェックし、次に `package.json` から name/version/publisher を読んで `extension.vsixmanifest` と `[Content_Types].xml` を生成し、最後に `zip -q -X -r` で固めます。収録するのは実行時に必要なファイルだけ（`src/*.js`、`syntaxes/`、`snippets/`、`language-configuration.json`、`package.json`、`README.md`）で、`tests/`、`CONTRACT.md`、`.vscodeignore` はパッケージに入りません。システムに `zip` が要ります。

## テスト

```bash
node --test "vscode/gugugaga/tests/*.test.js"   # 167 条，11 个文件
npm run test:all                                # 134 + 100 + 167 = 401 条
```

4 条のエンドツーエンド用例は実際に `node bin/gg.ts 嘎嘎` を spawn して本物のフレームをデコードするので、見かけの緑ではありません；9 条の純粋性用例は出力パネルの実行時ゲートに対して挙動テストと変異テストを行います；すべてオフライン、依存ゼロで、`require("vscode")` は**しません**（ホストのモックは `Module._load` でフックします）。

## 既知の制限

- LSP は実装していません：補完とホバーはコンテキストの走査 + 正規表現で、ファイルを跨ぐ意味解析、ジャンプ、リネームはありません。
- 診断は `node` と `咕咕嘎嘎`（またはワークスペースの `bin/gg.ts`）に到達できることが前提です；環境が整っていないと診断は静かに出なくなり、原因は DevTools にしか出ません。
- `gugugaga.maxSteps` は現時点では効きません（`嘎嘎` はプログラムを実行しないからです）。
- untitled バッファにはパスがないので、検査の対象になりません。
- 実際の VS Code ホストでは起動していません：ハイライト、折りたたみ、スニペットのジャンプ、ホバーの見た目、設定画面の表示は、いずれも静的・オフラインの証拠しかありません。
- Windows での PATH 探索の `PATHEXT` 分岐は実走していません（手元は macOS）。
