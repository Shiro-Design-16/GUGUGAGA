# ググガガ語（GUGUGAGA / 中国語表記：咕咕嘎嘎語）

> `咕` `嘎` `！` `？` `：` とスペースと改行とインデントだけで書く、純粋な OOP 言語です。
> ソースにアルファベットも数字も文字列もコメントもありません——名前はすべて `咕`/`嘎` のビット列で、出力はすべてビットストリームです。

**現状**：v1 は動いています。419 件のテストがすべて緑（言語 142 + トランスレータ 104 + 拡張機能 173）、7 つのサンプルプログラムが実行でき、実行時依存はゼロ（Node 24 の型ストリップで `.ts` をそのまま実行）。

---

## 0. これは何で、何ではないか

**である**：クラス、継承、フィールド、メソッド、コンストラクタ、`自己`（this）、動的ディスパッチ、静的エントリブロック、ローカルスコープ、`当`/`如果`/`返回`、ステップ上限と深さ上限を備えた、静的検査付きのインタプリタ言語です。Brainfuck より一段抽象度が高い——紙テープ操作ではなく「クラス」が書けます。

**ではない**：
- 実務のためのものではありません（性能は非目標、純粋なツリー走査インタプリタです）。
- 文字列も配列も例外もジェネリクスもコメントもありません。
- **人間が読めるテキストを出力しません**。プログラムが書けるのは裸のビットストリームだけです。「嗨」を見たければ別のプロジェクト——**咕嘎トランスレータ**が必要です（エンコードの約束は §4）。

## 1. クイックスタート

```bash
./install.sh            # 装一次：把 咕咕嘎嘎 / ググガガ / gggg / gg / ggt 链接到 PATH 上的目录
gggg examples/咕嘎咕嘎.咕咕     # 像 python x.py 一样直接跑；stdout = 24 位裸位流 = E5 97 A8 = 「嗨」
咕咕嘎嘎 嘎嘎 examples/嘎嘎咕咕.咕咕  # 只做词法/语法/静态检查，成功则完全静默
printf 35 | gggg examples/咕嘎嘎咕.咕咕
./demos/咕咕咕嘎.咕咕     # 首行 #! 的 .咕咕 文件本身就是可执行脚本
npm test                # node --test "tests/**/*.test.ts"
```

インストールしなくても動きます：`./bin/gg.ts examples/咕嘎咕嘎.咕咕`。入れ方は三通り、どれでも構いません：`./install.sh`（推奨。五つのコマンドが一度に入り、本リポジトリへシンボリックリンクされるので、コードを直せばすぐ反映されます）、`npm link`（ルートで `咕咕嘎嘎`/`ググガガ`/`gggg`/`gg` をリンクし、`translator/` でもう一度 `npm link` すれば `ggt` が入ります）、あるいは `bin/gg.ts` を好きな名前でシンボリックリンクするだけでも構いません。

ソースファイルの拡張子は四つ（大文字小文字を区別しません）：`.咕咕`、`.ググ`、`.gu`、`.gugugaga`。ファイル名とサンプル名はすべて純粋なビット名に変えました（`examples/咕嘎咕嘎.咕咕`、`examples/ガググガグ.ググ`、`examples/gugugaga.gu`）。ディレクトリ名は ASCII のまま（`src/`、`tests/`）——あれはホスト側ツールチェーンの骨格で、言語には関与しません。

**エラーもビットストリームです。** エラー時、stderr にあるのは `咕`/`嘎` の診断フレームだけで、文字は一行もありません——人間向けの文言はトランスレータが復元します：

```bash
咕咕嘎嘎 程序.咕咕 2> /tmp/咕 || ggt decode --diag /tmp/咕
# 2:7 E1001 非法字符“噶”（U+5676）
```

詳細は §11 と `SPEC.md` §12（GGDIAG v1）を参照してください。`gggg 文件.咕咕` は `run` サブコマンドを省けます：最初の非オプション引数が上記四つの拡張子のいずれか（または既存のファイル）なら、実行として扱います。

## 2. 文字集合：なぜちょうど八つの記号なのか

八つの記号に三通りの綴り（方言）があり、位置ごとに等価です——同じファイルの中でも、同じ単語の中でも混在できます：

| ビット | 中国語（既定） | 日本語 | 英語（大文字小文字を区別しない） |
| --- | --- | --- | --- |
| 0 | `咕` U+5495 | `グ` U+30B0、`ぐ` U+3050 も可 | `GU`：`Gu`/`gU`/`gu` のいずれも可 |
| 1 | `嘎` U+560E | `ガ` U+30AC、`が` U+304C も可 | `GA`：`Ga`/`gA`/`ga` のいずれも可 |

約物と空白も同じく等価です：`！`=`!`、`？`=`?`、`：`=`:`。インデントは半角スペース U+0020 でも全角スペース U+3000 でもよく、どちらも一桁と数えます。字句解析器が位置ごとに `咕`/`嘎` へ正規化し、その後の字句・構文・意味解析は中国語のビット列だけを相手にします。

| トークン | コードポイント | 用途 |
| --- | --- | --- |
| `咕` | U+5495 | ビット 0。同時に「プリント」の裸語としても使う |
| `嘎` | U+560E | ビット 1 |
| `！` | U+FF01 | 全角感嘆符：定義の接尾辞 / 呼び出しの接尾辞 |
| `？` | U+FF1F | 全角疑問符：値取得の接尾辞 |
| `：` | U+FF1A | 全角コロン：区切りの接尾辞境界（ブロック先頭、束縛、実引数、戻り値……） |
| スペース | U+0020 | 同じ行内のトークン区切り**だけ**に使う |
| 改行 | U+000A | 文の終端 |
| インデント | 4 個のスペースから | ブロック構造 |

八つの固い規則：
1. 約物は全角も半角も**合法**です（`！`=`!`、`？`=`?`、`：`=`:`）。中国語方言では既定で全角を書きます。本当に違法なのは文字集合にない文字です。
2. インデントは**スペースだけ**（半角 U+0020 か全角 U+3000、どちらも一桁、同じブロック内で混ぜても可）。最外層は 0 インデント、ブロック内は一貫して増える必要があります。タブ文字 Tab は E1001。
3. 読み込み時に CRLF は LF へ正規化されます。BOM は違法。
4. **コメント構文はありません**——コメントは九つ目の記号を持ち込み、「八つの記号だけ」という前提を壊してしまいます。
5. **文字列はありません**。文字列 = ビット列リテラルで、UTF-8 のバイトごとに 8 ビットという約束です（§4）。
6. **数値はありません**。整数 = 二進のビット列で、`嘎嘎嘎？` に続けてビットを密着させて書きます。
7. エンコードに関与するのはビット名だけです（`咕`/`グ`/`GU`、`嘎`/`ガ`/`GA`）。**注意：`噶`（U+5676）、`呷` など似て見える字はすべて違法**で、E1001 で止められてコードポイントが報告されます。英語の `g`/`G` は `GU`/`GA` の二文字に揃える必要があり、単独でも E1001 です。
8. 唯一の I/O：出力 = `咕：<表达式>` が裸のビットストリームを stdout へ書く。入力 = `嘎嘎嘎嘎嘎嘎嘎`（読入）が stdin から UTF-8 の次の一バイト（0..255）を読み、EOF では空を返します。

## 3. 言語の概観

> 本章の表はすべて中国語方言で書きます（`咕`/`嘎`）。他の方言は §2 の対応表どおり位置ごとに置き換えるだけで、たとえば `咕咕！` = `ググ！` = `GUGU!`。照合は正規化の後に行われるので、方言はどの規則にも影響しません。

### 3.1 予約語（21 個）と予約トークン（30 個）

**裸語（接尾辞なし、7 個）**

| 綴り | 意味 | Java |
| --- | --- | --- |
| `咕` | プリント（後ろに `：表达式` を続ける） | `System.out.write` |
| `嘎嘎` | リターン | `return` |
| `嘎嘎嘎` | もし | `if` |
| `嘎嘎嘎嘎` | そうでなければ | `else` |
| `嘎嘎嘎嘎嘎` | ループ | `while` |
| `嘎嘎嘎嘎嘎嘎` | 自分 | `this` |
| `嘎嘎嘎嘎嘎嘎嘎` | 読み込み | stdin から一バイト読む |

**宣言語（接尾辞 `！`、4 個）**：`咕咕！` クラス定義 ｜ `咕咕嘎！` メソッド定義 ｜ `咕咕嘎嘎！` プログラムのエントリ ｜ `咕嘎嘎！` インスタンス生成

**動作語（接尾辞 `！？`、2 個）**：`咕咕！？` 束縛（代入 / フィールド宣言） ｜ `咕嘎！？` 評価して捨てる

**値取得語（接尾辞 `？`、17 個）**

| 綴り | 名称 |
| --- | --- |
| `咕？` | 加算（整数の加算。二つのビット列なら連結） |
| `咕咕？` | 減算 |
| `咕嘎？` | 乗算 |
| `咕咕咕？` | 除算（ゼロ方向へ切り捨て） |
| `咕咕嘎？` | 剰余 |
| `咕嘎咕？` | 等値 |
| `咕嘎嘎？` | 小なり |
| `咕嘎嘎咕？` | 大なり |
| `咕嘎咕咕？` | 論理積（短絡しない） |
| `咕嘎咕嘎？` | 論理和（短絡しない） |
| `咕咕咕咕？` | 否定（単項） |
| `咕咕嘎咕？` | 符号反転（単項） |

名前を読む書き方は `<名字>？`。演算子は一律**前置記法**です：`咕？ a b` = `a + b`。括弧がないので前置しかありえません——これが唯一曖昧さのない選択です（§7）。

### 3.2 糖衣構文の一覧

| 綴り | 意味 |
| --- | --- |
| `咕咕！ <名字>` + インデントブロック | クラス定義 |
| `咕咕！ <子类>：<父类>？` + インデントブロック | 継承 |
| `咕咕！？ <名字>：<表达式>` | クラス本体では = フィールド宣言、文の中では = 代入 / 新しいローカル変数 |
| `咕咕嘎！ <方法名> [：<参数名>]*` + インデントブロック | メソッド定義。**メソッド名がクラス名と同じならコンストラクタ** |
| `咕咕嘎嘎！ <名字>` + インデントブロック | プログラムのエントリ（静的コンテキスト、「自分」はない） |
| `咕嘎嘎！ <类名>？ [：<实参>]*` | インスタンス生成 |
| `<接收者> <方法名>！ [：<实参>]*` | メソッド呼び出し |
| `<对象>？ <字段名>` | フィールド読み取り |
| `咕咕！？ <对象>？ <字段名>：<表达式>` | フィールド書き込み |
| 行末に `：` だけが残る | 糖衣構文：その行は空行と等価で、視覚的な整列のため |

### 3.3 完全なプログラム一つ（本当に動きます）

クラス `咕咕咕嘎`：フィールド二つ `嘎`=3、`嘎咕咕`=2。メソッド `嘎嘎嘎咕` は両者の和を返し、エントリはインスタンスを一つ作ってプリントします（64 ビット、値 5）。

```text
ググ！　グググガ：
　　　　ググ！？　ガ：ガガガ？ガガ
　　　　ググ！？　ガググ：ガガガ？ガグ
　　　　ググガ！　ガガガグ：
　　　　　　　　ガガ：グ？　ガ？　ガググ？
ググガガ！　グガガガ：
　　　　ググ！？　ガグガ：グガガ！　グググガ？
　　　　グ：ガグガ？　ガガガグ！
```

実測の出力は 64 ビット、下位三位が `嘎咕嘎`、デコードすると 5 です。

### 3.4 最初にいただいた仮の草稿との対照

いただいた骨格（`咕咕！ 咕嘎：` クラス定義、`咕咕！？ 咕：` 変数宣言、`咕咕嘎！ 咕咕嘎：` メソッド定義、`嘎嘎：` リターン、`咕咕嘎嘎！` エントリ、`咕嘎嘎！` インスタンス化、`咕嘎！？` 呼び出し）はほぼそのまま残しましたが、何箇所かは修正が必要でした：

1. 草稿にあった `噶`（U+5676）は合法な文字ではありません——あるのは `咕`/`嘎` だけです。そのためフィールド名・メソッド名は**予約語に占有されていないビット列**から取る必要があります（§5）。`咕`、`咕嘎` のような短い名前はキーワードに取られています。
2. 名前を読むには `？` 接尾辞が必要です：`咕` と書けばプリント文、`咕？` と書いて初めて「名前 `咕` の値を読む」になります。この接尾辞がないと、`咕`/`嘎嘎`/`嘎嘎嘎` はキーワードと衝突します。
3. メソッド呼び出しは `<接收者> <方法名>！` と書きます。`咕嘎！？` は「評価して捨てる」で、式全体の副作用に使います。
4. 草稿の `嘎嘎： 咕？ 咕咕嘎 嘎？` が「変数咕 + 変数嘎 を返す」の意味なら、`嘎嘎：咕？ 咕？ 嘎？` と書くべきです（前置記法：演算子が直後の二つの式を食べます）。

### 3.5 つまずきやすい文法の境界

`新建`（`咕嘎嘎！`）は**あらゆる式の起点**に置けます：束縛の右辺、二項演算の右オペランド、コロンの後の実引数スロット、フィールドの初期化値。ただし**すでに終わった式の直後には置けません**（前置記法に括弧はないので、そういう場面では先にローカル変数へ束縛します）。実引数の区切りはコロンだけなので、`m！：a：b` は実引数 2 個、`m！：a 咕嘎嘎！ C？` はやはり実引数 1 個です。

## 4. 出力エンコードの約束（咕嘎トランスレータのインタフェース）

stdout は**連続した裸のビットストリーム**です：ビット名 0 と 1 だけがあり、**区切りも改行も、末尾の改行もありません**。ビット名をどの字形で描くかはソースファイルの拡張子に従います（§10 と `SPEC.md` §8.1 を参照）：`.咕咕` → `咕`/`嘎`、`.ググ` → `グ`/`ガ`、`.gu`/`.gugugaga` → `GU`/`GA`。

| 値の型 | 出力ビット幅 | 説明 |
| --- | --- | --- |
| 整数 | **固定長 64 ビット**の補数表現、上位ビットが先 | 64 ビットを超えたら下位 64 ビットを取る |
| ビット列 | そのまま、ビットごとに写す | 長さはリテラルの長さ |
| ブール | **8 ビット**：偽 = `咕` 8 個、真 = `嘎` 8 個 | バイト境界に揃う |
| 空 / オブジェクト | — | E4006、出力できません |

**文字列の約束**：ビット列で表し、UTF-8 のバイトごとに 8 ビット、上位ビットが先、バイトを順に出力します（8 ビット整列を保つ）。エラー位置より前の出力は stdout に**残ります**（ストリーミングで、バッファしません）。

トランスレータの責務はこれで完全に決まります：stdin のビットストリームを読む → 約束どおりに切り分ける → 人間が読めるテキストを出力する。**この約束こそが、本プロジェクトと `translator/` の間の唯一の契約です。**

## 5. 名前経済学：なぜ変数が「嘎咕嘎」になるのか

名前 = 少なくとも一ビット以上の `咕`/`嘎` の列で、予約語と等しくてはいけません。その結果、使える名前空間は細かく刻まれます：

| 名前の長さ | 使える個数 | 例 |
| --- | --- | --- |
| 1 | 1 | `嘎` |
| 2 | **0** | —（`咕咕` `咕嘎` はどちらも占有済み） |
| 3 | 2 | `嘎咕咕` `嘎咕嘎` |
| 4 | 9 | `咕咕咕嘎` `嘎嘎嘎咕` … |
| 5 | 31 | |
| 6 | 63 | |
| 7 | 127 | |

サンプルの名前が長めなのはこのためです——短い名前はほぼキーワードに食べ尽くされます。`docs/名字对照表.md` は各サンプルのビット列を一行ずつ人間の言葉に訳し、Java の概念に対応づけています。

## 6. Java との対応

| Java | ググガガ語 |
| --- | --- |
| `class C { }` | `咕咕！ C：` + インデントブロック |
| `class D extends C` | `咕咕！ D：C？` + インデントブロック |
| フィールド宣言 | `咕咕！？ 字段名：初值`（クラス本体内。祖先から子クラスの順に初期化） |
| メソッド | `咕咕嘎！ 名字 [：参数]*` + インデントブロック |
| コンストラクタ | 名前がクラス名と同じメソッド。`新建 C：a：b` は実引数の個数で照合 |
| `this` | `嘎嘎嘎嘎嘎嘎`（自己） |

## 7. 設計上の取捨：いくつかの重要な選択

1. **行志向の文法 + インデントブロック**を選び、「一行にビット列を延々と並べる」形にはしませんでした。「独立した言語に見える」ためには読める構造が要ります。八つの記号しかない前提では、インデントがブロック構造を表す唯一の手段です（括弧もセミコロンもありません）。
2. **接尾辞でトークンの種類を符号化**しました：裸語 = 文 / キーワード、`！` = 宣言 / 呼び出し、`！？` = 動作、`？` = 値取得、`：` = 区切り境界。これでキーワードとユーザーの名前が衝突せず、しかも**最長一致で判定できます**——字句解析器は「ビット列の直後にどの接尾辞が来るか」だけを見てトークンの種類を決められます。
3. **式は一律前置記法**。括弧がない ⇒ 中置ではまとまりを作れません（`a+b*c` は解なし）。代償として、入れ子の実引数はいったんローカル変数で受ける必要があります（§8）。
4. **静的検査 + ツリー走査インタプリタ**で、AST 最適化もバイトコードも JIT もやりません。性能は非目標で、可読性を優先します（`src/interp.ts` 一ファイルで意味論のすべてを説明しきります）。
5. **出力 = 裸のビットストリーム**で、言語層では「文字列のプリント」をしません。人間が読める出力を一度許すと、文字集合に何十もの記号を詰め込むことになり、設計の前提が壊れます。可読性はトランスレータに任せます。
6. **コメント構文はなし**：コメントを足すと九つ目の記号を持ち込むことになります。

## 8. 既知の欠落（v1 の非目標。無かったことにせず書き残します）

- 括弧がない ⇒ 入れ子呼び出し `f(g())` は中間変数に分ける必要があります。`新建` はすでに終わった式の直後には置けません（§3.5）。
- 文字列 / 配列 / コレクション型はありません。文字列はビット列の約束にすぎません。
- 不等演算子も、以下 / 以上もありません。`与` + `非` + `相等` を組み合わせます。
- コメントはありません。
- 空のビット列は書けません（`嘎嘎嘎嘎？` の後ろに少なくとも一ビット密着させる必要があります）。
- I/O は一層だけ：stdout のビットストリーム + stdin のバイト。ファイルもネットワークもありません。
- 例外 / 捕捉はありません。実行時エラーで即終了します（すでに書いたビットは残ります）。
- 短い名前が不足しています（§5）。

## 10. CLI リファレンス

```text
用法：
  咕咕嘎嘎 <文件>                             # 执行，裸位流写 stdout（省略动作词，像 python x.py）
                                              # 后缀：.咕咕 / .ググ / .gu / .gugugaga（大小写不敏感）
  咕咕嘎嘎 嘎 <文件>.咕咕                     # 同上，显式写法
  咕咕嘎嘎 嘎嘎 <文件>.咕咕                   # 只做词法/语法/静态检查，成功静默
  咕咕嘎嘎 嘎嘎嘎                             # 帮助（帮助正文是一帧，走 stderr）
  咕咕嘎嘎 嘎嘎嘎嘎 <咕嘎位串> <文件>.咕咕     # 设步数上限（位串按二进制读）
退出码：0 成功；1 运行时错误；2 词法/语法/静态错误；3 用法错误
```

動作語はそれ自体がこの言語の文字です：`嘎`=実行、`嘎嘎`=検査、`嘎嘎嘎`=ヘルプ、`嘎嘎嘎嘎`=ステップ上限。ラテン文字の別名 `run`/`check`/`--help`/`--max-steps N` は手が覚えた古い習慣のために残しているだけで、**言語の語彙ではありません**。

コマンド名は `咕咕嘎嘎`（日本語の `ググガガ`、`gggg`、`gg` も同じ入口）。未インストール時の等価な書き方は `node bin/gg.ts ...`。拡張子は四つとも認識し、言語の方言と拡張子は無関係です——`.咕咕` に `GU` を書いても同じように動きます。ファイルの先頭行が `#!` で始まる場合、実行 / 検査の前に読み飛ばされます（空行に置き換え、行番号は変えません）。だから `.咕咕` ファイルは `./程序.咕咕` で直接動きます。`#` が他の行にあれば E1001 のままです。

ステップ上限のビット列：`咕`/`嘎` だけを含み、`咕`=0、`嘎`=1、上位ビットが先——`嘎` は 1、`嘎咕咕咕` は 8、`嘎嘎嘎嘎嘎` は 31。空列、他の文字を含むもの、値が 0 のものは、すべて用法エラーです。

**出力の字形はソースファイルの拡張子に従います**：プログラムのビットストリームと診断フレームは同じビット名を使うので、同じプログラムの stdout と stderr は常に同じ方言になります。ヘルプとコマンドラインの用法エラーには具体的なプログラムがないため、常に中国語の `咕`/`嘎` を使います。

**診断はすべて（ヘルプも用法エラーも）stderr に書かれます**。stdout にあるのはプログラムのビットストリームだけです。なので `咕咕嘎嘎 嘎嘎嘎 | less` は空です。ヘルプを見るには `咕咕嘎嘎 嘎嘎嘎 2>&1 | ggt decode --diag` が必要です。

実行時の制約：ステップ上限は **5 000 000**（文の実行と式ノードの評価がそれぞれ 1 ステップ。`嘎嘎嘎嘎` / `--max-steps` で変更可）、呼び出し深さの上限は **512**。stdin が端末のときは空入力として扱い、対話のまま止まらないようにします。

### 11.1 診断の読み方

エラーコードと位置はすべて **GGDIAG v1 フレーム**に入っています（`SPEC.md` §12）：stderr にあるのは `咕`/`嘎` だけで、文字が読めないのは正常です。トランスレータに渡します：

```bash
咕咕嘎嘎 程序.咕咕 2> /tmp/咕 || ggt decode --diag /tmp/咕
# 2:7 E1001 非法字符“噶”（U+5676）
```

ヘルプフレーム（`咕咕嘎嘎 嘎嘎嘎`）も同じです。**ビット名の字形はソースファイルの拡張子に従います**：`.咕咕` のフレームは `咕`/`嘎`、`.ググ` は `グ`/`ガ`、`.gu` は `GU`/`GA`；ヘルプと用法エラーは常に中国語です。正規化すれば三方言のフレームはビット単位で同じで、`ggt decode --diag` は三つとも食べます。人間向けの文言は今も `src/` に書かれていますが、それは**運ばれるバイト列**にすぎません——フレームが原文の UTF-8 を抱えているので、トランスレータはどの文言も知る必要がなく、インタプリタと文言を同期させる必要もありません。`ggt decode --diag` の出力の最初の部分は `行:列` です。位置を持たないイベント（ファイルが読めない、用法エラー）にはコード名と説明だけが付きます。

## 13. 姉妹プロジェクト：咕嘎トランスレータ（実装済み、`translator/` を参照）

本リポジトリの言語側の責務は「裸のビットストリーム + エンコードの約束（§4）」までです。ビットストリームを人間の言葉に戻すのは `translator/` の担当です（独立したサブプロジェクト：独自の `package.json` / `README.md` / 104 件のテスト、依存ゼロ、本リポジトリのモジュールは一切 import しません）。ビットストリームに加えて、**診断フレーム**を人間の言葉に訳すのも担当します（`ggt decode --diag`、§11 参照）：

```bash
cd translator
../bin/gg.ts run ../examples/咕嘎咕嘎.咕咕 | node bin/ggt.ts decode --bytes   # 嗨
../bin/gg.ts run ../examples/咕嘎咕嘎.咕咕 | node bin/ggt.ts decode           # 嗨（stderr 说明猜到了 bytes）
printf 35 | ../bin/gg.ts run ../examples/咕嘎嘎咕.咕咕 | node bin/ggt.ts decode --plan plans/咕嘎嘎咕.plan  # 104 / -2
printf 嗨 | node bin/ggt.ts encode --as-literal    # 嘎嘎嘎嘎？+ 24 位，可直接粘进源码
```

デコードモード：`--plan <文件>`（スロット表による厳密なデコード）、`--int64`、`--bytes`（UTF-8 厳格）、`--hex`、`--bits`。モードを指定しない場合は 64/8 の倍数で推測し、説明は stderr に書きます。逆向きの `encode` はテキスト、`--int64` の十進、`--as-literal`（ビット列 / 整数リテラルを生成）に対応します。どちらも三方言を認識します：`decode` は `咕嘎`/`グガ`/`GUGA` の混在を食べ、`encode --ja` / `--en` は方言どおりにビット列を出力します（`--ja` と `--en` は排他）。plan はホスト層の ASCII 行指向ファイル：`int64` / `bits <n>` / `bytes <n>` / `bool`。

plan が要る理由：ビットストリームは自己記述的ではなく、`64 位整数` と `3 个字节的位串` はバイトレベルでは区別できません。だから「厳密な解釈」には人がスロット表を与える必要があります。おおよそでよければ推測モードを使います。

ルートで `npm run test:all` を実行すると三者分のテストが続けて走ります（言語 142 + トランスレータ 104 + エディタ拡張 173 = 419 件）。

## 14. エディタサポート：VS Code 拡張機能（`vscode/`）

動くだけでは足りません。そこで書きたいと思わせる必要があります。リポジトリには依存ゼロの VS Code 拡張機能が入っています：一度インストールすれば `.咕咕`、`.ググ`、`.gu`、`.gugugaga` のファイルでエディタ体験が得られます。

```bash
code --install-extension vscode/gugugaga-language.vsix    # 安装
```

インストール後、上記四つの拡張子のファイルをどれでも開くと、ステータスバーの言語モードに「咕咕嘎嘎语」と表示され、六つの機能が使えます：

| 機能 | 挙動 |
| --- | --- |
| 言語の基本 | 四つの拡張子の認識（`.咕咕`/`.ググ`/`.gu`/`.gugugaga`）、`：` で終わる行の自動インデント、`嘎嘎`/`嘎嘎嘎嘎`/`嘎嘎嘎嘎嘎嘎` でのインデント後退、インデントによる折りたたみ、コメント構文なし |
| ハイライト | 30 個の予約トークン + 整数 / ビット列リテラル（ビット列はまとめて着色）+ クラス名 / メソッド名 / 変数名 + `！？`/`：` の約物、35 条の TextMate 規則。各規則は三方言（`咕\|グ\|ぐ\|[Gg][Uu]`）と半角約物を同時に扱います |
| 補完 | コンテキスト（トップレベル / クラス本体 / 文の位置 / 式の位置 / 呼び出しの後）に応じて予約語と骨格スニペットを出します。`！？` の後は、その文書で定義済みのメソッド名だけを出します |
| ホバー | トークンの意味、一族の所属、用法の例——すべて 咕/嘎 で書かれています（外側の純粋性、下記参照） |
| 診断 | 開く / 保存 / 編集（デバウンス既定 350ms）のたびに本物の `咕咕嘎嘎 嘎嘎` を走らせ、stderr の GGDIAG フレームをデコードして、`E1xx`~`E3xx` を波線と Problems パネルの項目に変えます |
| 実行 | エディタのタイトルバーの ▶（および右クリックメニュー）が `咕咕嘎嘎 <文件>` を統合ターミナルへ送ります。`python x.py` と同じ感覚です。未保存のドキュメントはまず保存し、ターミナルは再利用し、出力と終了コードはターミナルに残ります |

実行ボタンは意図的に**出力を奪いません**：ビットストリームの行き先はターミナルです。そうしてこそ stdin を食わせながら結果を `ggt decode` へ渡せます。暗黙実行（動作語なし）を使い、引数の組み立てはプラットフォームごとに引用符を掛け、ショートカットは割り当てません（コマンドパレットに ASCII のキー和音が出ると外側の純粋性が壊れるからです）。

さらに 8 条のスニペット（クラス、コンストラクタ、メソッド、エントリ、フィールド、条件、ループ、新建式）があり、本文には 咕/嘎/！/？/：/スペース/改行 以外の文字はありません。

設計上、記しておく価値のある取捨が三つあります：

1. **診断は中途半端な解析器を別に書くのではなく**、本物のインタプリタを呼びます：拡張機能は `咕咕嘎嘎 嘎嘎 <文件>` を spawn し、stderr の GGDIAG フレームを `{行, 列, 码}` に戻します（`src/diagnostics.js` は依存ゼロのデコーダを自前で持ち、リポジトリのモジュールは import しません）。エディタに表示されるコードと説明は、ターミナルで解いた結果と完全に同じです。代償は CLI に到達できること：設定 `gugugaga.cliPath` → ワークスペースの `bin/gg.ts` → PATH 上の `咕咕嘎嘎`/`ググガガ`/`gggg`/`gg` の三段フォールバックでコマンドを探します。
2. **外側も純粋な咕嘎です**：設定ページのタイトルと説明、コマンドのタイトル、出力パネル、Problems パネルのソース列と項目本文（本文はその診断のフレーム全体のビット列で、`ggt decode --diag` に渡して初めて人間の言葉になります。コード名列はわざと空のままにしています。さもないと `E1001` が描画されてしまうからです）、補完候補の説明、ホバーの文言、スニペットの説明——すべて 咕/嘎/！/？/：/スペース/改行 だけで書かれています。`cliPath` の既定値は `咕咕嘎嘎` そのもので、診断コレクション名も `咕咕嘎嘎` です。パネルには実行時のゲートも一つあります：`isPureLine()` が認めない行はパネルに書かず、開発者コンソールにだけ出します（`tests/purity.test.js` はこのゲートが本当に拒むことをミューテーションテストで示しています）。調査情報（exec/args/ワークスペース/スタック）は開発者コンソールへ退避します——ユーザーには見えませんが、裏を返せば「診断が出ない理由」を全部見るには DevTools を開く必要があるということです。マニフェストに残る ASCII はすべて VS Code スキーマのマッチングキー（拡張機能 id、`scopeName`、コマンド id、設定 id）で、一文字変えると拡張機能が読み込まれません。
3. **TextMate は lookbehind を使えません**。そこで各着色規則は左境界のキャプチャグループ `(^| +)` / `(^| +|：)` を一つ食べてから、そのグループに色を付けます。そうしないと、クラス先頭の規則が呼び出し名 `嘎咕咕嘎咕！` の 3 文字目で `咕咕！` に一致し、`咕咕？` が値取得の名前の中で減算と見なされます——これはこの文法全体で最も重要な設計の一つです。

三つのコマンド（現在のファイルを実行 / 現在のファイルを検査 / 出力パネルを表示）、五つの設定（`cliPath`、`nodePath`、`checkOnChange`、`debounceMs`、`maxSteps`）。構造と再パッケージの説明は `vscode/README.md` にあります。

拡張機能には 11 個のテストファイル、173 条のアサートが付属し、すべてオフライン、依存ゼロ、`require("vscode")` は**禁止**です。そのうち 3 条は本当に `node bin/gg.ts 嘎嘎` を spawn し、stderr のビットストリームを診断に戻します（偽の緑ではありません）。したがって、このプロジェクトで実機検証のない唯一の成果物がこれです：配色、折りたたみの手触り、スニペットの Tab 移動、ホバーのポップアップの見た目には静的・オフラインの証拠しかなく、実際の VS Code ホストで起動したことはありません。この点は隠さずここに書いておきます。


## 15. 多言語ドキュメント

九つの主要ドキュメントには日本語と英語の訳があり、ファイル名は `原文.ja.md` / `原文.en.md` で、原文と並んで置かれています：

| 中国語 | 日本語 | English |
| --- | --- | --- |
| `README.md` | `README.ja.md` | `README.en.md` |
| `TUTORIAL.md` | `TUTORIAL.ja.md` | `TUTORIAL.en.md` |
| `SPEC.md` | `SPEC.ja.md` | `SPEC.en.md` |
| `translator/README.md` | `translator/README.ja.md` | `translator/README.en.md` |
| `translator/CONTRACT.md` | `translator/CONTRACT.ja.md` | `translator/CONTRACT.en.md` |
| `vscode/README.md` | `vscode/README.ja.md` | `vscode/README.en.md` |
| `vscode/CONTRACT.md` | `vscode/CONTRACT.ja.md` | `vscode/CONTRACT.en.md` |
| `vscode/gugugaga/README.md` | `vscode/gugugaga/README.ja.md` | `vscode/gugugaga/README.en.md` |
| `docs/名字对照表.md` | `docs/名字对照表.ja.md` | `docs/名字对照表.en.md` |

翻訳の規則は `docs/翻译规范.md` に凍結されています：コードブロック内の**ソース**例は方言どおりに書き換えます（日本語は `グ`/`ガ` + 全角スペースのインデント、英語は `GU`/`GA` + 半角約物）。一方、**プログラムの出力、コマンド、パス、数字、エラーコード**は一律に写します——訳文はツールに代わって事実を美装してはいけません。先頭には `<!-- i18n:begin -->` のブロックがあり、言語の切り替えに使います。中国語の原文が常に正本です。

`node scripts/check-translations.mjs`（`npm run test:i18n`）は 18 個の訳文を機械的に検査します：i18n ヘッダー、見出し階層の並び、コードブロックの数と言語マーカー、ソースブロックの方言等価（一文字ずつ 0/1 に正規化して比較）、出力ブロックの逐字一致、数字の多重集合、パスの集合。さらに、エントリを持つ完全なサンプルを一つずつ**実際に走らせて** stdout のビットストリームを比較します。数字が一つずれても、パスが一つ抜けても、ビット名の文字を一文字書き換えても赤になります。

三つのエンジニアリング文書の役割分担：`SPEC.md` は言語仕様（権威）、`README.md`（本文）は設計の説明と取捨、`TUTORIAL.md` は入門チュートリアルです。
