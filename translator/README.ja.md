# 咕嘎トランスレータ（ggt）

ググガガ語（中国語表記: 咕咕嘎嘎語）のプログラムが stdout に書く裸のビットストリームを、人間が読めるテキストにデコードします。逆向きに、テキスト / 整数をビットストリームにエンコードすることもできます。
依存ゼロ、純粋な ESM、.ts は Node 24 の型ストリッピングにそのまま渡して実行します。

## 使い方

    ggt decode [--plan <文件>] [--int64|--bytes|--hex|--bits] [<位流文件>]
    ggt decode --diag [<位流文件>]
    ggt encode [--int64|--as-literal] [--ja|--en] [<文本文件>]
    ggt --help

ファイルを渡さなければ stdin を読み（stdin が端末のときは空入力として扱います）、ファイルを渡したらそのファイルを読んで stdin は無視します。

    cd translator
    ../bin/gg.ts run ../examples/咕嘎咕嘎.咕咕 | node bin/ggt.ts decode --bytes
    # 嗨

    printf 35 | ../bin/gg.ts run ../examples/咕嘎嘎咕.咕咕 | node bin/ggt.ts decode --plan plans/咕嘎嘎咕.plan
    # 104
    # -2

## デコードモード

- --int64：64 ビットごとに区切り、符号付き十進で出力して、一塊ごとに一行にします。
- --bytes：UTF-8 として厳密にデコードし、不正な並びはエラーにします。末尾に改行は追加しません。
- --hex：16 バイトごとに一行、`0000: E5 97 A8  |...|` の形で出力します（オフセットは四位の大文字十六進、ASCII の列は印字できないバイトを点にします）。
- --bits：8 ビットずつ組にしてスペースで区切り、一行に 8 組、末尾に改行は追加しません。
- --plan：plan ファイルに従ってスロットごとに出力し、すべてのビットを正確に消費しなければなりません（一ビット多くても少なくてもエラーです）。
- モードを指定しない場合：64 の倍数なら --int64、そうでなく 8 の倍数なら --bytes、それ以外は --bits と推測します。その説明は stderr に書き、stdout には結果だけを出します。
- --diag：推測はせず、ホストの GGDIAG v1 診断フレームを直接デコードします（次の節を参照）。上記五つのモードとは排他です。
- どのモードでも、入力のビットストリームは三方言の混在でかまいません（「方言」を参照）。--diag も同じで、診断フレームのビット名の字形はプログラムの方言に従います（.ググ なら グ / ガ、.gu なら GU / GA）。フレームの構造は変わりません。

## 終了コード

0 成功、1 入力 / デコードのエラー、2 用法エラー、3 plan ファイルのエラー。

## エンコード方向

- ggt encode：stdin / ファイルのテキストを UTF-8 でバイトのビットストリームにエンコードし、既定では純粋な 咕 / 嘎 を出力します。
- ggt encode --as-literal：テキストでは 嘎嘎嘎嘎？ の接頭辞を付け、--int64 と組み合わせたときは 嘎嘎嘎？ の接頭辞を付けます。
- ggt encode --int64：十進の記号（空白区切り、負号可、範囲 -2^63 .. 2^63-1）を入力し、64 ビットの補数で一つずつ出力します。
- ggt encode --ja：ビット名を グ / ガ に変え、句読点も全角にします。生成されるリテラルの接頭辞は ガガガガ？ / ガガガ？ です。
- ggt encode --en：ビット名を GU / GA に変え（一ビットが二文字なので出力は二倍の長さになります）、句読点は半角です。接頭辞は GAGAGAGA? / GAGAGA? です。
- --ja と --en は排他で、同時に渡すと用法エラーになります（終了コード 2）。この二つのスイッチは encode 専用で、decode に渡すと「未知のオプション」になります。

## 方言（入力は三方言、出力は二つのスイッチ）

ビットストリームの入力は SPEC.md §1.1 の三つの書き方を受け付けます。位置ごとに等価で、同じ入力の中で混ぜてもかまいません：

| ビット | 中国語 | 日本語 | 英語（大文字小文字を区別しない） |
| --- | --- | --- | --- |
| 0 | 咕 | グ（ぐ も可） | GU / Gu / gU / gu |
| 1 | 嘎 | ガ（が も可） | GA / Ga / gA / ga |

- 英語のビット名は ASCII 二文字を対で読み、gu が 0、ga が 1 です。単独の g / G は他の文字と同じく不正な文字としてエラーになります（終了コード 1）。
- 空白はなお空白・タブ・改行・復帰で、さらに **U+3000 の全角スペースも空白として扱います**（SPEC §1.1、日本語ソースのインデント）。
- 内部では一律 咕 / 嘎 に正規化するので、plan ファイル、GGDIAG フレームの構造、診断の本文は変わりません。変わるのはフレームに載る字形だけで、--diag も同じ正規化で読みます（英語のビット名は二文字で一ビット）。
- 書き方が変わるのは decode の入力側と encode の出力側だけで、ビットストリームそのもの、モードの意味、終了コードは変わりません。

    printf 41 | node bin/ggt.ts encode --ja                # ググガガグガググググガガグググガ
    printf 41 | node bin/ggt.ts encode --ja --as-literal   # ガガガガ？…（粘回日语源码）
    printf 41 | node bin/ggt.ts encode --en                # GUGUGAGAGUGAGUGUGUGUGAGAGUGUGUGA
    printf 'ググガガグガググググガガグググガ' | node bin/ggt.ts decode --bytes   # 41

    # 生成的日语位串直接当 咕咕嘎嘎 程序的位串字面量
    BITS=$(printf 41 | node bin/ggt.ts encode --ja)
    printf '咕咕嘎嘎！ 嘎咕嘎嘎嘎咕\n    咕：嘎嘎嘎嘎？%s\n' "$BITS" > /tmp/ja.ググ
    ../bin/gg.ts run /tmp/ja.ググ | node bin/ggt.ts decode --bytes   # 41

## 診断フレーム（--diag）

ホストはエラー報告を SPEC.md §12 の GGDIAG v1 フレームとして stderr に書き（位名の字形だけが 咕 / 嘎、グ / ガ、GU / GA とプログラムの方言に従います）、--diag はそれを人間の言葉に戻して、一フレーム一行で出します：

    ../bin/gg.ts run 不存在的.咕咕 2>&1 | node bin/ggt.ts decode --diag
    # 读文件失败 无法读取文件 不存在的.咕咕：ENOENT: no such file or directory, open '不存在的.咕咕'

    ../bin/gg.ts 咕咕 2>&1 | node bin/ggt.ts decode --diag
    # 用法错误 用法错误：未知子命令 咕咕（执行程序请直接写文件路径，例如 咕咕嘎嘎 程序.咕咕）

行の形式：

    12:3 E2002 未定义的变量 x     位置があるとき：行:列 コード名 本文
    用法错误 未知子命令“foo”     位置が 0 のとき：コード名 本文

- コード名：1–21 は SPEC.md §9 の E1001…E4012 です（順序がそのままエラーコード表）。0 は用法エラー、22 はヘルプ、23 はファイル読み込み失敗、24 は内部エラー、それ以外は 未知事件 <码> と出力します。
- ビット名は三方言で正規化します（咕 / グ / GU は 0、嘎 / ガ / GA は 1、大文字小文字は区別せず、英語は二文字で一ビット）。ホストの警告、フレーム間の空白や改行は一律で無視するので、stderr の全文をそのまま繋げてかまいません。
- フレームの境界：magic(1010) / version(00) が合わなければ一ビットずつ後ろにずらして探し続けます。end が 110 でないフレームは丸ごと捨て、メッセージが書き切られていない（切り詰められた）フレームも捨てますが、どちらも後ろのフレームを飲み込みません。
- フレームが一つもないとき：stderr に一行 ggt: 没有找到诊断帧 を出し、終了コード 1。
- --diag は --plan / --int64 / --bytes / --hex / --bits と排他で、同時に渡すと用法エラーになります（終了コード 2）。

## 実装構造

- src/bits.ts：ビットストリームの解析、補数の変換、UTF-8 の厳密なデコード、GgtError。
- src/plan.ts：plan ファイルの解析とスロット幅。
- src/decode.ts：五つのデコードモードと、モード未指定時の推測。
- src/encode.ts：テキスト / 整数のエンコードとリテラルの接頭辞。
- src/diag.ts：GGDIAG v1 診断フレームのデコード、コード名の対応、一フレーム一行の整形。
- src/cli.ts：引数の解析、stdin の同期読み込み、終了コード。
- bin/ggt.ts：shebang 付きの入口で、import "#cli"（後述）。

## 契約で確定していない部分の判断

1. bin でのモジュール解決：契約は bin/ggt.ts が CLI の実装を再利用することを求め、さらに検証側は translator/bin に ../src が出ないことを求めています。
   解決策は package.json の imports で "#cli" -> "./src/cli.ts" と対応させ、bin では import { main } from "#cli" と書くことです。
2. --hex の ASCII 列：契約 §2.1 は常に |印字可能な ASCII| 列を付けると定めていますが、§5 の例には十六進しか書かれていません。
   ここでは常に ASCII 列を出力します（印字できないバイトは点）。行末は改行で、オフセットは 0000 から四位の大文字です。
3. --bits は末尾に改行を追加しません。空のビットストリームは空文字列を出力します。
4. plan の bool は 8 個の 咕（偽）か 8 個の 嘎（真）しか認めず、混ざったビットは壊れた入力としてエラーにします。
5. plan の構文：# で始まる行全体のコメントと空行は無視し、行の途中の # は余計な記号として扱います。引数は ASCII の十進の正整数だけを受け付け
   （+1、1e3、1.5 はすべて拒否）、bits 0 も拒否します。空の plan は合法です（このときどんな非空のビットストリームも残りありとしてエラーになります）。
6. encode --int64 は任意の負号 + ASCII 数字だけを受け付け、+1 も途中に挟んだ空白も拒否します。空の入力は空の出力になります。
7. リテラルモードでは値ごとに接頭辞が付きます。負数はリテラルモードではエラーになります（ソースに負数のリテラルはありません）。
8. テキストモードは入力の各バイトをそのままエンコードします。末尾の改行も含み、trim はしません。
9. エラーメッセージは一律 "ggt: " の接頭辞を付け、終了コード 2 のときは用法も stderr に書きます。
10. --help / -h はどこに現れても優先して処理し、0 を返します。
11. stdin が TTY のときは空入力として扱い、対話が固まるのを避けます。stdin の読み込みは readSync のループで、EAGAIN のときは少し眠って再試行します。
12. --int64 / --plan は項目ごとに一行で末尾に改行を付け、--bytes は改行を追加しません（デコードしたテキストをそのまま出力）。
13. 入力ファイルが読めない = 終了コード 2、plan ファイルが読めない = 終了コード 3。
14. --diag が他のモードと排他のときは、契約の「2 = 用法エラー」に従って終了します（タスク文書には 3 と書かれていたことがありますが、ここでは CONTRACT.md を優先します）。
15. 位置が半分だけ（行番号が非 0、列番号が 0）のときも「行:列」を出力し、行番号は落としません。行も列も 0 のときだけ位置を省きます。本文が空のときは末尾の空白を出力しません。
16. フレームのエラーでは一ビットずつずらして再同期し、「主張されたメッセージ長」は飛ばしません：切り詰められたヘッダは雑音かもしれず、その後ろに完全なフレームがあるかもしれないからです。
17. 診断の本文は非厳密な UTF-8 でデコードします（壊れたバイトは U+FFFD）。一バイトの破損でフレーム全体を失うべきではありません。
18. 三方言が効くのは「入力の解析」と「encode の出力」の二箇所だけで、内部のビットストリーム、plan のスロット、GGDIAG フレームは一律 咕 / 嘎 です。方言がプロトコル層に染み出さないようにしています。--diag は入口で SPEC §1.2 に従って正規化するので、フレームの構造は一ビットも変わりません。
19. --en のビット名は二文字で一ビットなので、出力の長さはビット数の二倍になります。gu と GA を混ぜて書いても解析できます（大文字小文字を区別しません）。
20. --ja / --en は encode にだけ付き、decode に新しいオプションは増やしません：decode の出力はもともと人間の言葉なので、方言は要らないからです。
21. --diag の英語のビット名は二文字を対で読む（文字数で長さを数えない）ので、ホストの警告にたまたま gu / ga の文字対が現れると一ビットとして扱われます。これは三方言が共有する固有の曖昧さで、プロトコルが保証するのはビット名の字形だけです。

## テスト

    cd translator && npm test

node:test + node:assert/strict で、全部で 104 項目：bits / decode / plan / encode / cli / diag / dialect / e2e の八つのファイルです。
CLI のテストは spawnSync で node bin/ggt.ts を走らせ（実行権限には依存しません）、e2e は ../bin/gg.ts でビットストリームを生成します。

## plan ファイル形式（正確なデコード）

ホスト層の ASCII 行指向ファイルで、`plans/` の下に置き、あるビットストリームのスロット構造を記述します：

```text
# 以 # 开头为注释，空行忽略
int64        # 64 位补码整数，输出有符号十进制
bits <n>     # n 位位串，原样输出
bytes <n>    # n 个字节 = 8n 位，按 UTF-8 输出
bool         # 8 位布尔，输出 真 / 假
```

`int64` / `bool` / `bytes` はそれぞれ一行で出力し、`bits <n>` は位串をそのまま出力してから改行します。スロットは**正確に消費**しなければなりません——一ビット多くても少なくてもエラーです（終了コード 1）。plan 自体の構文エラーは行番号を報告します（終了コード 3）。

既存の例：`plans/咕嘎咕嘎.plan` の中身は `bytes 3`（24 ビットに相当）、`plans/咕嘎嘎咕.plan` は `int64` が二行（128 ビットに相当）です。

なぜ必要か：ビットストリームには自己記述の枠組みがなく、`64 位整数` と `3 个字节的位串` はバイトの並びとしては区別できません。そのため「正確な解釈」には人が与えるスロット表が要ります。plan を渡さないときに限り、推測モードになります。
